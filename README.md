# SmartPrice 🇧🇬 — реален продукт

Мобилно приложение (React Native Expo + TypeScript) със **собствен PostgreSQL** и
**собствен Node/TypeScript API**. Дизайнът и структурата на приложението са
запазени — сменен е само източникът на данни: вече няма симулации.

**Публикувано на: https://smart.lookthis.online**

> ⚠️ **Валута:** България е в еврозоната и Stripe вече отказва BGN
> („The currency bgn is no longer supported. Use eur instead.“).
> Затова даренията са в **EUR**. Останалите цени в приложението все още се
> показват в „лв.“ — пълната миграция към € е отделно решение.

## Публикуване (как е устроено)

```
Интернет → Cloudflare (smart.lookthis.online)
         → Cloudflare Tunnel "smartprice"  → localhost:3030
         → контейнер "smart" (nginx)
              ├── /            → статично Expo web приложение
              ├── /api/*       → контейнер smartprice-api:4000
              └── /uploads/*   → контейнер smartprice-api:4000
         → контейнер smartprice-db (PostgreSQL 16)
```

Един домейн, един тунел, три контейнера. nginx проксира API-то, затова няма
CORS проблеми и API-то не е изложено директно.

```bash
docker compose up -d --build     # db + api + web
bash server/final_check.sh       # типове + контейнери + публичен домейн
```

Тунелът: отделен тунел `smartprice` (не пипа основния `lookthis`).
Конфиг `~/.cloudflared/smart-config.yml`, автоматичен старт
`Startup\cloudflared-smart.vbs`.

## Архитектура

```
SmartPrice/
├── app/                 # екрани (expo-router)
│   ├── (auth)/          # вход и регистрация
│   ├── (tabs)/          # Поток, Радар, Сподели, Общност, Профил
│   └── post/[id].tsx    # детайл на публикация
├── components/          # UI компоненти (запазен дизайн)
├── context/AppContext   # единен източник на данни за UI-а (върху API-то)
├── src/
│   ├── api/client.ts    # типизиран HTTP клиент, JWT + авто-refresh
│   ├── auth/            # AuthContext (сесия, вход, изход)
│   └── lib/format.ts    # дати/пари на български
├── server/              # ← API-то
│   ├── src/routes/      # auth, posts, comments, media, donations, community
│   ├── migrations/      # SQL схема (прилага се автоматично при старт)
│   ├── smoke_test.py    # 90 реални проверки срещу работещ сървър
│   └── Dockerfile
└── docker-compose.yml   # PostgreSQL 16 + API
```

**Защо собствен API, а не директна връзка към базата:** мобилно приложение не може
да пази парола за база данни. API-то държи тайните (JWT, Stripe, OpenRouter) и
налага правилата. Supabase е премахнат напълно — базата е твоя.

## Стартиране

```bash
# 1. Конфигурация (има .env.example)
cp .env.example .env
# попълни поне POSTGRES_PASSWORD и JWT_SECRET (openssl rand -base64 48)

# 2. База + API
docker compose up -d --build

# 3. Проверка
curl http://127.0.0.1:4000/api/health
python server/smoke_test.py        # 90 проверки

# 4. Приложението
npm install
npx expo start                     # i / a / w
```

`EXPO_PUBLIC_API_URL` в `.env` трябва да сочи към IP-то на компютъра
(напр. `http://192.168.1.171:4000`), за да работи на реален телефон в същата WiFi.
`API_HOST_BIND=0.0.0.0` отваря API-то за локалната мрежа (по подразбиране е само localhost).

## Какво е включено и какво иска ключ

| Функция | Без ключ | С ключ |
|---|---|---|
| Вход / регистрация / профили | ✅ работи | — |
| Публикации, снимки, реакции, коментари | ✅ работи | — |
| Търсене, филтри, сортиране, класация | ✅ работи | — |
| Ценови аларми | ✅ работят | — |
| **OCR на касови бележки** | ❌ честно 503 | `OPENROUTER_API_KEY` |
| **Дарения** | ❌ честно 503 | `STRIPE_SECRET_KEY` (+ webhook) |

Липсващият ключ **никога не се заменя с фалшиви данни** — сървърът връща 503 и
ясно съобщение кое липсва.

### OCR (реален)
`OPENROUTER_API_KEY` + `OCR_MODEL` (по подразбиране `google/gemini-2.5-flash`).
Моделът чете само това, което вижда на снимката; ако нещо не се чете — връща null,
вместо да измисли. Endpoint: `POST /api/ocr/receipt`.

### Stripe (реален)
`STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET`. Използва се **Stripe Checkout** —
картата се въвежда на страницата на Stripe, приложението никога не я вижда.
`donations.status` става `succeeded` **само** от webhook-а (или при проверка на
сесията директно в Stripe), не от клиента.

Webhook за локална разработка:
```bash
stripe listen --forward-to http://127.0.0.1:4000/api/donations/webhook
# сложи получения whsec_... в STRIPE_WEBHOOK_SECRET и рестартирай API-то
```

## Схема на базата (основното)

- `profiles` — потребители (bcrypt парола, роля, статус на дарител, точки доверие)
- `posts` — публикации (полярност, категория, цени, грамаж, GPS, статус за модерация)
- `receipts` + `receipt_items` — касови бележки (с проверка сумите да са аритметично верни)
- `post_reactions`, `post_helped_marks`, `post_bookmarks`, `comments`, `comment_likes`
- `price_history` — история и потвърждаване на цени
- `price_alerts`, `donations`, `badges`, `profile_badges`, `content_reports`, `uploads`
- Изгледи: `v_posts_full` (пост + автор + агрегирани реакции), `v_leaderboard`

Цялостността е в базата: CHECK ограничения, външни ключове, тригери за броячите и
за статуса на дарител (задейства се само при **преход** към `succeeded`).

## Промени спрямо оригиналния код (важно)

Оригиналното приложение изглеждаше готово, но беше демонстрация. Поправено:

**Симулации → реални неща**
- Плащанията бяха фалшиви (`success: true` с измислен `pi_stripe_XXXX`) → реален Stripe Checkout + webhook
- OCR-ът връщаше твърдо зададени бележки с измислени ЕИК-та → реален vision модел
- Нямаше автентикация → регистрация/вход с bcrypt + JWT (access + refresh)
- Данните се четяха само от устройството → реален PostgreSQL през API

**Махнати фалшиви твърдения**
- „Умна кошница“ сравняваше измислени цени на Lidl/Kaufland/Billa/Фантастико → сега пази твоите цени и сравнява с реалните публикации
- AI асистентът показваше измислени „обичайни цени“ (зехтин 24 лв., нощувка 120 лв.) → сега казва честно „нямаме данни“
- `add.tsx` измисляше референтна цена (`total × 1.65`) и после показваше „спестяване“ → само потребителят я въвежда
- „100% Проверени ревюта“ → „0 платени ревюта“ (второто е вярно)
- Общността показваше „Събрани 580 от 800 лв.“ → реално събраното този месец от базата

**Поправени бъгове**
- Категория „Други“ беше позволена в UI, но забранена в базата → insert-ът винаги падаше
- Мерната единица беше винаги `'g'` (и за течности) → реален избор г/кг/мл/л/бр.
- `personal_saved_bgn` се вдигаше с измислени 25 лв. → реална разлика, с отмяна
- Тригерът за дарения броеше сумата два пъти при update → само при преход
- Странични ефекти в React state updater-и → изнесени
- Липсваха RLS/права политики → правата се налагат от API-то
- Броячите в Радар не се показваха (грешен регистър на ключовете)
- Нямаше тестове → `server/smoke_test.py` с 90 проверки
